# Meowcute 视频生成序列帧方案分析

- 分析目标：解释当前视频生成序列帧链路的耗时不稳定原因，并评估更适合游戏精灵的替代方案。
- 结论：正式生产建议采用“AI 拆部件 + 确定性 2D 骨骼动画”；视频生成保留为动作参考和预览模式。

## 一 结论摘要

当前方案的主要问题不是抽帧算法，而是把一个需要“固定角色、固定尺寸、固定循环”的游戏精灵任务交给了随机视频扩散模型。视频模型的自动重试、时序长度、显存搬运和逐帧抠图共同造成耗时波动，也带来闪烁、糊帧和配件漂移。

建议分成两个工作流：

1. **Stable Sprite 默认生产模式**：AI 只负责一次性生成或拆分角色部件，后续用 2D 骨骼和确定性渲染输出精灵帧。
2. **AI Motion 预览模式**：HunyuanVideo 生成短视频，用于探索动作；确认动作后再提取关键姿势或套入骨骼，不直接把视频帧作为正式精灵素材。

## 二 当前链路

相关实现：

- `backend/app/pipelines/walkvideo.py`：方向计划、视频生成、动作评分和自动重试。
- `backend/app/providers/hy15.py`：HunyuanVideo-1.5 的帧数对齐、步数和 offload。
- `backend/app/providers/diffusers_local.py`：视频管线加载、显存策略和推理。
- `backend/app/pipelines/sequence.py`：周期检测、抽帧、去重、剔除糊帧和逐帧抠图。
- `backend/app/pipelines/matte.py`：u2net、GrabCut、颜色键和 alpha 清理。

当前流程：

```text
参考图
  ↓
方向立绘推导
  ↓
HunyuanVideo / Wan 生成视频
  ↓
GIF 解码
  ↓
动作周期检测
  ↓
抽帧和去重
  ↓
逐帧抠图
  ↓
保存透明 PNG
  ↓
精灵表
```

八方向模式通常是 5 个真实方向加 3 个镜像方向。真实方向需要分别生成立绘和视频，方向之间基本串行执行。

## 三 耗时不稳定的根因

### 1 自动重试让总耗时不可预测

`generate_walk()` 根据 `motionThreshold` 判断动作幅度是否合格。动作幅度不足时会重新执行完整的视频推理：

- HunyuanVideo 增加步数；
- Wan 增加 CFG 和步数；
- 每次重试都是完整视频生成。

默认最多可能执行三次，因此同一输入可能出现一次、两次或三次视频推理的差异。

### 2 HunyuanVideo 的帧数存在非线性退化

项目注释和实测记录了以下情况：

| 帧数 | 单步耗时特征 |
|---|---|
| 21 帧 | 约 2.4 秒/步 |
| 33 帧 | 约 5 秒/步 |
| 61 帧 | 约 47 秒/步，基本不可用 |

因此帧数不是简单的线性成本。超过 33 帧后，时序 token 数会造成明显退化。

### 3 模型加载和显存搬运造成长尾

视频底座需要 CPU offload。项目还刻意把方向立绘推导和视频生成分成两个阶段，以避免两个大模型互相驱逐显存，但这会带来：

- 首次加载时间；
- CPU 和 GPU 之间的权重搬运；
- 显存释放和重新分配；
- 不同方向之间的冷启动波动。

### 4 多方向任务是串行任务

`run_walk()` 按方向顺序执行真实方向视频。GPU 资源有限时无法简单并行，因此总耗时约等于各方向耗时相加，单方向的波动会直接放大到整批任务。

### 5 序列帧阶段还要逐帧抠图

默认配置约为：

```text
8 个方向 × 每方向 8 帧 = 64 次抠图
```

每帧可能经过：

```text
u2net → GrabCut → 颜色键
```

CPU 负载、输入尺寸和 fallback 路径都会影响耗时。抠图还可能损伤脚、披风、武器和细小配件。

### 6 GIF、PNG 和拼条图会产生尾部耗时

模型推理结束后，系统还要解码 GIF、保存逐帧 PNG、生成拼条图和重新保存 GIF。当前总耗时没有把这些阶段拆开记录，用户只能看到一个聚合结果。

## 四 替代方案比较

| 方案 | 耗时稳定性 | 画面一致性 | 实现成本 | 适合定位 |
|---|---|---|---|---|
| AI 拆部件 + 2D 骨骼动画 | 很高；生成部件后主要是轻量渲染 | 最高；部件跨帧不重绘 | 中等 | 正式游戏精灵生产，推荐 |
| 短视频 13～21 帧 + 插帧 | 中等 | 中等；仍可能形变和漂移 | 中等 | 动作预览或非严格像素素材 |
| 关键帧图像生成 + 确定性插值 | 中高 | 中高；优于整段视频 | 中高 | 复杂动作折中方案 |
| 继续换视频模型 | 不确定 | 不确定 | 高 | 不建议作为首选 |
| 逐帧图像重绘 | 低 | 低；最容易闪烁 | 低到中 | 不建议 |

## 五 推荐方案 AI 拆部件加确定性骨骼动画

项目已经有这条路线的实验基础：

- `tools/rigwalk_spike.py`
- `tools/rigwalk2.py`
- `tools/rigwalk3.py`
- `tools/rigwalk_ghibli.py`
- `tools/exp_exploded_parts.py`
- `tools/godotrig/build_rig.py`

推荐流程：

```text
角色参考图
  ↓
Qwen-Image-2.1 生成爆炸拆解图或透明部件
  ↓
获得头、躯干、双臂、双腿、披风等 RGBA 部件
  ↓
自动或人工标注关节锚点
  ↓
前向运动学骨骼动画
  ↓
确定性渲染 8～16 帧
  ↓
精灵表、GIF、Godot 资源
```

### 优点

- 每次渲染耗时稳定；
- 角色不会跨帧重新绘制；
- 不会出现脸、胡须、背包和武器随机闪烁；
- 首尾帧可以数学上闭合；
- 不需要视频解码；
- 不需要每帧运行 u2net；
- 动作参数可编辑；
- 可以直接导出 Godot 骨骼资源。

### 主要风险

- 披风、裙摆和长发容易被错误归类；
- 部件连接处可能露缝；
- 自动关节点对非标准比例角色不一定准确；
- 侧面和背面不能简单复用正面骨架。

建议保存角色级 `rig.json`，至少包含：

```json
{
  "parts": {},
  "anchors": {},
  "bones": {},
  "clips": {},
  "renderSettings": {
    "integerPixel": true,
    "resample": "nearest"
  }
}
```

第一次由用户校准关节点，后续待机、行走、奔跑和攻击只修改动作曲线，不重新生成角色图。

## 六 第二方案 短视频加插帧

如果仍希望使用 AI 产生自然动作，可以改成：

```text
HunyuanVideo 生成 13～21 帧
  ↓
保留关键帧
  ↓
RIFE / FILM / 光流插帧
  ↓
抽取 8～16 帧
```

适合动作预览和非严格像素素材，但不能完全消除模型闪烁：光流只能补运动，不能修复角色细节变化；手、脚和武器可能出现扭曲；像素画经过光流后还可能产生非整数像素。

## 七 第三方案 关键帧图片生成加确定性插值

可以用 Qwen-Image-2.1 生成少量动作关键帧，例如：

```text
静止帧 → 接触地面帧 → 抬腿帧 → 另一侧接触地面帧
```

然后使用部件级仿射变换、局部遮罩和少量光流补帧。关键帧数量可控，也更容易并行；但每张关键帧仍是独立生成，不能达到骨骼方案的完全确定性。

项目已有实测表明 Qwen-Image-2.1 单张约 13～19 秒、峰值约 14.7GB，并且支持原生 RGBA，因此可以作为部件生成或关键姿势生成底座。

## 八 其他视频模型的判断

LTX-Video 官方仓库支持图生视频、多关键帧条件、关键帧动画和视频插值：

<https://github.com/Lightricks/ltx-video>

它适合作为“短视频加关键帧”实验对象，但仍需要重新验证像素风和角色保真度。AnimateDiff 采用运动模块注入 Stable Diffusion 的路线，集成灵活，但模型组合复杂，角色一致性需要重新调参：

<https://github.com/guoyww/AnimateDiff>

HunyuanVideo-1.5 本身已经支持图生视频，主要问题是它不适合作为严格游戏精灵帧的唯一生产底座：

<https://github.com/Tencent-Hunyuan/HunyuanVideo-1.5>

## 九 免费动作素材库和授权建议

先区分两类资源：

1. **可直接套用的动作数据**：包含骨骼、关键帧、插槽或动画曲线，例如 Spine JSON、DragonBones 数据或 Godot AnimationPlayer 资源。这类资源才是真正意义上的“复用动作”。
2. **只有图片帧的免费素材**：例如精灵表、角色 PNG 和 GIF。它们可以复用视觉素材，但不能直接套到新角色的骨骼上，通常需要重新拆部件或重新绑定。

### 推荐来源

| 来源 | 适合获取什么 | 能否直接复用动作 | 授权和注意事项 |
|---|---|---|---|
| [Kenney Assets](https://kenney.nl/assets) | CC0 的角色部件、像素素材、精灵图和基础游戏素材 | 通常不能直接提供通用 2D 骨骼动作；适合拿来做部件和测试角色 | Kenney 官方说明资产页上的游戏素材使用 CC0，可用于商业项目且不强制署名；仍应保留下载时的许可证文件 |
| [OpenGameArt](https://opengameart.org/) | 精灵表、角色图、动画帧、部分骨骼和引擎资源 | 取决于具体资源，有些可用，有些只有 PNG/GIF | 每个资源单独检查 CC0、CC-BY、CC-BY-SA、GPL 等许可；必须记录作者、原链接和许可证 |
| [Godot Asset Library](https://godotengine.org/asset-library/) | Godot 插件、Skeleton2D 示例、AnimationPlayer 工具和可运行示例 | 可直接复用 Godot 场景或动画资源，但数量和角色类型有限 | 以资源页面的许可证为准；项目已有 Godot 骨骼导出脚本，优先选择 Godot 4 资源 |
| [Spine 官方示例与导出格式](https://us.esotericsoftware.com/spine-json-format) | Spine skeleton、skin、slot、attachment 和 animation 数据 | 可以复用动作数据，但需要 Spine Runtime 或转换器 | Spine JSON 可以表达骨骼、皮肤和动画；第三方动作包的商业授权必须单独确认，不能只看“免费”标签 |
| itch.io 免费标签 | 像素角色、动画帧、部件包、少量 Spine/DragonBones 工程 | 多数是图片帧；少数会提供可编辑工程 | 授权由作者决定，必须查看每个项目的 License、商用限制和署名要求 |
| GitHub 开源项目 | 动画编辑器、Godot 导入器、动作转换器和示例数据 | 取决于仓库，适合构建转换工具链 | 同时检查代码许可证和素材许可证；仓库开源不代表其中的美术素材也可自由商用 |

### 对 Meowcute 最有价值的组合

建议按下面的优先级使用免费资源：

```text
第一优先：免费动作数据或 Godot AnimationPlayer 资源
第二优先：Spine/DragonBones 工程，转换为项目自己的 MotionClip
第三优先：只有精灵表的素材，拆成部件后重新绑定
第四优先：3D 动作库，仅作为动作节奏和关键姿势参考
```

Kenney 更适合提供 CC0 的部件和测试素材，而不是提供完整的人形骨骼动作。OpenGameArt 的资源种类更丰富，但许可证必须逐个核验。Godot Asset Library 适合直接参考和复用 Godot 4 的 Skeleton2D、AnimationPlayer 与工具脚本。Godot 官方文档说明 Skeleton2D/Bone2D 可以组成 2D 骨架，AnimationTree 可以用于动作混合，因此这条路线与项目当前的 Godot 导出方向一致：[Godot 2D Skeleton](https://docs.godotengine.org/en/stable/tutorials/animation/2d_skeletons.html)、[Godot AnimationTree](https://docs.godotengine.org/en/4.0/tutorials/animation/animation_tree.html)。

### 不建议直接把免费精灵表当作动作库

精灵表通常绑定了原角色的：

- 身高和比例；
- 画布尺寸；
- 关节位置；
- 前后遮挡关系；
- 帧数和帧率。

它可以作为动作参考，但不能像 `walk.json` 那样直接套给另一个角色。要实现跨角色复用，必须拿到骨骼动作数据，或者先把原角色拆成部件并重新绑定。

### 免费资源入库规范

每个下载的动作或部件都建议保存一份 `asset_manifest.json`：

```json
{
  "name": "example-walk",
  "source": "https://example.com/asset",
  "author": "author-name",
  "license": "CC-BY-4.0",
  "commercialUse": true,
  "attributionRequired": true,
  "modified": true,
  "notes": "动作数据已重定向到 humanoid_2d_v1"
}
```

项目要商用时，至少保留下载地址、作者、许可证原文或许可证文件、下载日期和修改记录。不要因为资源页面写着“free”就默认可以商用。

## 十 不改架构时的短期优化

| 优先级 | 改动 | 目标 |
|---|---|---|
| P0 | HunyuanVideo 默认固定 17 或 21 帧，禁止默认进入 33 帧以上 | 控制单方向耗时 |
| P0 | 自动重试默认改为 0，动作不足只标记 | 避免耗时突然变成 2～3 倍 |
| P0 | 记录 load、derive、video、decode、sample、matte、save 各阶段耗时 | 建立 P50/P95 基线 |
| P1 | 按参考图和参数 hash 缓存立绘、视频帧和序列帧 | 重复执行直接复用 |
| P1 | 首帧或关键帧使用 u2net，后续用颜色键和掩码传播 | 减少逐帧分割 |
| P1 | 对已带 alpha 的输入跳过重复抠图 | 减少错误和 CPU 时间 |
| P2 | 用可控 CPU worker pool 处理各方向序列帧 | 缩短后处理尾部 |

## 十一 实施路线

### 第一阶段 建立基线

为每个方向和每个阶段记录：

- 耗时；
- 显存峰值；
- 重试次数；
- 输入帧数；
- 输出帧数；
- 抠图方法；
- fallback 和失败原因。

同一角色连续运行 5 次，记录平均值、P50、P95 和最大值。

### 第二阶段 正式接入 Stable Sprite 节点

复用 `tools/rigwalk_ghibli.py` 的部件和骨架逻辑，定义统一数据结构：

```text
parts
anchors
bones
clips
renderSettings
```

先支持单方向，再扩展到正面、侧面和背面三个锚点，最后用镜像和插值补齐八方向。

### 第三阶段 增加人工校准和资产复用

用户第一次确认关节点后保存 `rig.json`。动作修改只调整曲线，不重新运行角色生成。

### 第四阶段 保留 AI 视频预览节点

AI 视频用于探索动作。用户选定动作后，提取关键姿势或映射到骨骼，再生成正式精灵帧。

## 十二 验收指标

| 指标 | 建议目标 |
|---|---|
| 同参数重复运行耗时 | P95 / P50 ≤ 1.5 |
| 自动重试放大倍数 | 默认不超过 1 次，最好改为手动触发 |
| 固定部件跨帧一致性 | 颜色、轮廓和配件不随机变化 |
| 循环闭合 | 骨骼相位闭合，不重复保存首帧造成跳变 |
| 像素质量 | 整数像素对齐，最近邻缩放，无抗锯齿边缘 |
| 失败恢复 | 单个方向失败不丢弃其他方向，可从缓存继续 |
| 可编辑性 | 可重新绑定关节点和动作曲线 |

## 十三 最终建议

把“AI 拆部件 + 确定性骨骼动画”定为正式生产方案，把 HunyuanVideo 保留为动作探索和预览方案。短期通过限制帧数、取消默认重试、缓存中间结果和减少逐帧抠图，可以降低当前方案的波动；长期只有把跨帧角色像素从随机视频生成中移出，才能同时解决耗时稳定性、闪烁、配件丢失和循环闭合问题。
